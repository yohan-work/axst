# 01. 평가 축 — 정의와 배정 규칙

## 왜 5축인가

팀스파르타가 운영하는 기업용 AI 역량 진단은 **프롬프트 엔지니어링 / 데이터 분석 / 윤리와 보안 / 워크플로우** 4축이다. 검증된 구조이고 이 진단의 출발점이기도 하다.

문제는 원문이 도달한 결론이 그 4축 어디에도 없다는 점이다.

> 문제는 기술이나 비용이 아니라 **"무엇을 AI에게 맡길 것인가"를 명확히 아는 것**이다.

같은 행사에서 LilysAI의 5인 팀이 "의사결정만 사람이 하고 수행은 다 AI가" 하면서 **안 맡기는 것은 콘텐츠 제작과 고객 소통 딱 두 가지**라고 밝힌 것도 기법 얘기가 아니다. 위임 경계를 어디에 그을지에 대한 판단이다.

그래서 **위임 판단력을 1축으로 올렸다.** 그리고 데이터 분석은 독립 축에서 빼 검증 축에 흡수했다 — 전사 공통 시험에서 데이터 분석을 독립 축으로 두면 비분석 직무에 불공정하고, 실제로 필요한 능력은 "분석할 수 있는가"가 아니라 "AI가 낸 분석을 믿어도 되는지 판단할 수 있는가"이기 때문이다.

| 팀스파르타 4축 | 본 진단에서 |
|---|---|
| 프롬프트 엔지니어링 | → **작업 설계(DSN)**로 재정의. 기법이 아니라 맥락·제약·규격의 지시 |
| 데이터 분석 | → **검증·신뢰 조정(VER)**에 흡수 |
| 윤리와 보안 | → **리스크·거버넌스(RSK)** |
| 워크플로우 | → **워크플로우 재설계(FLW)**. '전환 증명' 하위요소 추가 |
| *(없음)* | → **위임 판단력(DEL)** 신설 |

## 축 정의

축은 **주제**가 아니라 **분석 단위 + 실패 시 손해**로 정의한다. 주제로 정의하면 문항의 30% 이상이 축 간 충돌을 일으킨다(특히 DEL↔FLW, VER↔RSK).

| # | 축 | 코드 | 분석 단위 | 묻는 것 | 실패 시 손해 |
|---|---|---|---|---|---|
| 1 | 위임 판단력 | `DEL` | 단일 과업 1개 | 어디까지 AI에 넘기고 무엇을 사람이 보유하는가 | 책임 귀속이 불가능한 산출물이 나온다 |
| 2 | 작업 설계 | `DSN` | 1회의 지시 — 생성 **이전** | 맥락·제약·산출물 규격을 어떻게 지시하고 다음 턴으로 수렴시키는가 | 쓸 수 없는 산출물이 나와 재작업한다 |
| 3 | 검증·신뢰 조정 | `VER` | 생성된 산출물 1개 — 생성 **이후** | 무엇이 틀렸나, 어디를 먼저 보나, 얼마나 믿나 | 틀린 근거로 의사결정한다 |
| 4 | 워크플로우 재설계 | `FLW` | 2단계 이상 또는 2인 이상의 흐름 | 단계 제거·핸드오프·전파·전환 증명 | 개인 생산성만 오르고 조직은 그대로다 |
| 5 | 리스크·거버넌스 | `RSK` | 행위의 허용 여부 | 이 입력/출력/공개가 규정·권리상 허용되는가 | 법적·계약적·평판 손해가 난다 |

### DEL — 위임 판단력

단일 과업을 앞에 두고 **어디까지 AI에 넘기고 무엇을 사람이 쥐는지** 결정하는 능력. 기준은 작업량이 아니라 **책임이 귀속되는 판단인지, 되돌릴 수 없는 결정인지**다.

측정하는 오개념: 검수만 하면 판단까지 위임해도 된다 / AI가 생성한 안 중에서 고르는 것을 사람의 판단이라고 착각한다(겉보기 human-in-the-loop) / 시간이 없으면 AI를 회피한다.

### DSN — 작업 설계

**생성 이전**의 지시 설계. 수신자·용도, 투입 데이터의 범위와 출처, 금지·제약, 산출물 구조·분량·형식, 톤/품질 기준 또는 예시. 그리고 결과가 기대와 다를 때 다음 턴으로 수렴시키는 방법.

"프롬프트 기법"이 아니다. 기법을 외웠는지가 아니라 **업무 맥락을 지시로 옮길 수 있는지**를 본다.

### VER — 검증·신뢰 조정

**생성 이후**의 판단. 무엇이 틀렸는지 찾고, **무엇을 먼저 볼지 우선순위를 정하고**, 이 산출물을 어느 정도까지 믿을지 조정한다. 검증 우선순위의 기준은 `의사결정에 직접 쓰이는가 × 원자료로 재현 가능한가`다.

데이터 분석 능력을 여기에 흡수했다. 단 "분석할 수 있는가"가 아니라 "AI가 낸 수치를 믿어도 되는지 판단할 수 있는가"를 묻는다.

### FLW — 워크플로우 재설계

개인의 태스크가 아니라 **흐름**을 다룬다. 2단계 이상 또는 2인 이상이 관여하고, 정답이 순서·단계·핸드오프·전파를 바꾼다.

**필수 하위요소 3종** — 문항이 여기에 분포해야 한다. ③이 빠지면 FLW는 DEL의 복제품이 된다.

| | 하위요소 | 무엇을 보는가 |
|---|---|---|
| ① | 단계 소멸 | 업무 단계를 실제로 없애는가, 아니면 기존 단계에 AI를 덧붙이는가 |
| ② | 핸드오프·전파 | 다른 사람이 이어받을 수 있게 만드는가, 타인·팀에 확산시키는가 |
| ③ | **전환 증명** | 절감한 시간이 무엇으로 바뀌었는지 보고할 수 있는가 |

③의 근거는 원문의 측정 트랩이다 — 시간 절감으로만 보고하면 임원이 "남는 시간에 뭘 했는지"를 묻고, 2차 보고부터는 누가 썼는지 / 어떤 업무에 썼는지 / **그 업무를 어떤 다른 일로 전환했는지**를 써야 한다.

### RSK — 리스크·거버넌스

**허용 여부**를 다룬다. 정확성 문제가 아니라 권한 문제다. 판별문: **"정답을 맞혀도 허락 없이는 못 하는 일인가?"**

사내 데이터·개인정보·고객 정보·미공개 재무/인사 정보의 투입, AI 산출물의 사외 공개, 저작권·고지 의무, 편향.

## 축 배정 결정트리

출제자는 순서대로 실행하고 **먼저 걸리는 곳이 축이다.** 토픽으로 고르지 않는다.

```
1. 오답이 규정·권리·계약 위반을 낳는가? (정확성이 아니라 허용성)
   판별문: "정답을 맞혀도 허락 없이는 못 하는 일인가?"
   → 예: RSK

2. 이미 생성된 산출물을 제시하고 그 결함·신뢰도를 묻는가?
   (생성 전 지시를 묻는다면 아니다)
   → 예: VER

3. AI에게 줄 지시문·조건·형식을 묻는가?
   → 예: DSN

4. 과업이 2단계 이상 또는 2인 이상이 관여하고,
   정답이 순서·단계·핸드오프·전파를 바꾸는가?
   판별문: "정답이 바뀌면 다른 사람의 일이 바뀌는가?"
   → 예: FLW

5. 단일 과업의 위임 범위·최종 판단 보유자를 묻는가?
   → 예: DEL
```

**결정트리 몇 번에서 걸렸는지를 `axis_note`에 반드시 1줄로 남긴다.** 나중 감사·재분류 비용이 0에 가까워진다.

## 타이브레이커

실제로 충돌하는 네 쌍의 판정 규칙.

### VER vs RSK
손해가 **"확인하면 사라지는가"**(VER) vs **"안 하거나 허락을 받아야 사라지는가"**(RSK).

> **규칙: 제3자 노출·외부 공개가 문항의 핵심 조건이면 RSK.**

환각 인용을 사외 문서에 넣는 상황은 1차 RSK(공개·제3자 노출이 개입). 사내 검토용 문서라면 VER.

*출제 함의*: VER 문항을 쓸 때 지문에 "고객사에 그대로 전달된다" 같은 조건을 넣으면 그 문항은 자동으로 RSK가 된다. VER 문항의 지문은 사내 용도로 한정한다.

### DSN vs VER
**생성 이전 = DSN, 생성 이후 = VER.**

"프롬프트에 '출처를 표기하라'를 넣는다" → DSN. "출처 표기가 실제인지 확인한다" → VER.

### DEL vs RSK
제약의 출처가 **품질·책임·역량이면 DEL**, **규정·권리면 RSK**.

"인사 원천데이터를 외부 도구에 넣어도 되나" → RSK(규정). "채용 최종 합불 판단을 AI에 맡겨도 되나" → DEL(책임 귀속).

### DEL vs FLW
과업 1개는 DEL, 흐름은 FLW.

> **판별문: "정답이 바뀌면 다른 사람의 일이 바뀌는가?" 예면 FLW.**

## 강제 규칙

**MC 문항은 정확히 1개 축만 측정한다.** 두 축에 걸친다고 느껴지는 아이디어는 MC로 쓰지 않고 주관식(FR)으로 보낸다. 주관식은 애초에 축을 교차 통합하도록 설계됐다.

## 알려진 한계

DEL과 FLW는 경험적으로 상관이 0.5 이상 날 것으로 예상된다(둘 다 "무엇을 AI에 넘기는가"를 다루고 분석 단위만 다르다). 진단 목적에는 문제가 없지만, **두 축을 독립적인 레이더 스포크로 제시하면 안 된다.** 리포트 제약은 [04-scoring.md](04-scoring.md) 참조.
