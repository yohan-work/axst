# training/ — 진단 결과에 맞춘 실습 키트

진단은 **어디가 약한지**를 알려주고, 이 폴더의 키트는 **그 약한 곳을 연습하게** 한다. 개인 리포트의 "다음 행동" 칸이 가리키는 곳이 여기다.

처방 원칙(레벨별 트랙, 코호트 편성, 교육으로 안 풀리는 것)은 [docs/06-prescription.md](../docs/06-prescription.md)가 정본이다. 이 폴더는 그중 **"약점 축 → 교육 내용"을 실제로 해볼 수 있는 자료**로 만든 것이다.

## 키트 목록

| 역량 (축) | 이런 신호일 때 | 키트 | 상태 |
|---|---|---|---|
| 검증·신뢰 조정 (VER) | 🟠 보완 필요 · ⚪ 판정 보류 / 주관식 검증 설계 3점 이하 | [ver-frontend.md](ver-frontend.md) · [해설](ver-frontend.answers.md) | ✅ 프론트엔드·웹퍼블리싱판 |
| 위임 판단력 (DEL) | 〃 | — | 작성 예정 |
| 작업 설계 (DSN) | 〃 | — | 작성 예정 |
| 워크플로우 재설계 (FLW) | 〃 | — | 작성 예정 · **교육만으로 안 풀림**(흐름을 바꿀 권한이 필요하다, docs/06 §4) |
| 리스크·거버넌스 (RSK) | 〃 | — | 작성 예정 · **사내 데이터 등급표가 교육보다 효과적**(docs/06 §2) |

검증 키트를 먼저 만든 이유: 합성 파일럿(S0)에서 검증 축 평균 정답률이 25%로 가장 낮은 축 중 하나였고, 프론트엔드 업무에는 "AI가 쓴 PR 요약·QA 결과를 믿고 배포하는" 장면이 매일 있다.

## 키트를 만드는 원칙

새 키트를 쓸 때 지킨다. 검증 키트가 이 원칙의 첫 사례다.

1. **시험 문항을 재사용하지 않는다.** 원리는 같게, 장면은 새로 만든다. 교육이 시험 문항을 가르치면 재진단이 무의미해진다.
2. **정답이 키트 안의 자료만으로 확정되게 만든다.** diff, 로그, 사내 문서 발췌를 자료로 주고 그 안에서 판정한다. 외부 사실("공식 문서에 따르면")에 기대면 작성자가 틀릴 수 있고 학습자도 확인하기 어렵다.
3. **진단 리포트의 "생각의 습관" 문구를 해설에서 그대로 부른다.** 학습자가 "리포트가 말한 게 이거구나"를 알아보게 한다. 문구의 정본은 각 문항 파일의 `distractor_dx`다.
4. **마지막 실습은 본인 업무로 한다.** 점검표는 주관식 채점 기준과 같은 틀로 만든다 — 연습이 그대로 재진단으로 이어진다.
5. **교육으로 안 풀리는 것은 팀 장치로 넘긴다.** 키트 끝에 팀에 둘 장치(템플릿·체크리스트)를 하나씩 붙인다.
6. **직무별로 만든다.** 장면이 내 일이 아니면 학습자가 옮겨 쓰지 못한다. 검증 키트는 프론트엔드·웹퍼블리싱판이고, 다른 직무판은 같은 뼈대에 장면만 바꾼다.

## 팀 세션 진행안 (60분)

혼자 45분짜리를 팀 세션으로 돌릴 때.

| 시간 | 할 일 |
|---|---|
| 0–3분 | 각자 키트 0번(지금의 나)을 적는다. 공유하지 않는다 |
| 3–10분 | 진행자가 규칙 한 장(1절)을 읽는다 |
| 10–25분 | 실습 1을 **혼자** 푼다. 순서표만 채운다 |
| 25–35분 | 둘씩 짝지어 순서를 비교하고, **1번이 다른 짝**이 전체에 이유를 말한다 |
| 35–40분 | 진행자가 해설의 모범 순서와 "습관이 드러나는 자리" 표를 보여준다 |
| 40–45분 | 실습 2를 함께 푼다 |
| 45–58분 | 실습 3을 각자 시작한다. 끝내지 못하면 과제로 |
| 58–60분 | 0번 답을 다시 보고, 무엇이 바뀌었는지 한 줄 |

**진행자 주의**: 실습 1에서 누가 틀렸는지 지목하지 않는다. 이 진단의 결과는 교육 설계에만 쓰고 평가에 쓰지 않는다는 원칙([docs/00-charter.md](../docs/00-charter.md))이 세션에도 적용된다.

## 팀에 두는 장치: PR 템플릿 세 줄

실습 1이 보여준 세 가지 함정을 PR 템플릿에 넣는다. 교육은 잊히지만 템플릿은 매번 보인다.

```markdown
### AI가 쓴 요약을 그대로 올렸다면 확인
- [ ] "없음 · 전체 · 문제없음" 주장을 실제로 찾아봤다 (다른 사용처, 돌지 않은 테스트)
- [ ] 통과했다는 검사의 **범위**를 확인했다 (어느 폴더, 몇 개 스위트)
- [ ] AI가 할 수 없는 일("브라우저에서 확인", "모니터링 결과")을 지우거나 사람이 확인했다
```

## 효과를 확인하는 법

| 언제 | 무엇을 | 무엇이 변하면 효과인가 |
|---|---|---|
| 키트 직후 | 0번과 5번의 답 비교 | 첫 확인 대상이 "없다·전체" 주장으로 옮겨갔다 |
| 2~4주 뒤 | 팀 PR에서 세 줄 점검 사용 여부 | 체크된 PR에서 범위 오류·근거 없는 문장이 걸러졌다 |
| 8~12주 뒤 | 재진단 ([docs/06 §6](../docs/06-prescription.md#6-재진단)) | 검증 축 신호가 🟠 → ⚪/🟢, 주관식 검증 설계 점수 상승 |

재진단은 공개된 폼 A가 아니라 **비공개 시행 폼**으로 한다([docs/08](../docs/08-administration.md#폼-분리-공개-참조-폼과-시행-폼)).
